# 명예 외국인 — 의사결정과정

**기준일:** 2026-10-07
**근거:** `docs/superpowers/specs/`의 설계 문서, 커밋 메시지, 작업 대화 기록

기능 자체는 [기능정의서](feature-definition.md)에 정리했다. 이 문서는 **왜 그렇게 만들었는지**를 시간순으로 남긴다.

각 결정은 다음 형식을 따른다.
- **상황:** 결정이 필요했던 이유
- **선택지:** 검토한 대안
- **결정:** 고른 방식
- **이유:** 고른 근거
- **대가:** 감수한 한계와 나중에 바꿀 조건

## 결정 원칙

모든 결정에 공통으로 적용한 기준이다 (`CLAUDE.md`).

1. 가장 단순하고 유지보수하기 쉬운 방법을 먼저 고른다.
2. 새 패턴보다 기존 코드와 패턴을 재사용한다.
3. 불필요한 의존성과 인프라를 늘리지 않는다.
4. 비용은 무료 플랜 범위 안에 둔다.
5. 프로젝트 전체에 영향을 주거나 되돌리기 어려운 결정은 먼저 확인한다.

## D-01. 서버 없이 정적 사이트 + 빌드 시점 사전 생성

- **상황:** OpenAI로 단어를 만들어야 하지만, 서버 비용은 0원이어야 하고 API 키가 브라우저에 노출되면 안 된다.
- **선택지**
  1. 브라우저에서 OpenAI 직접 호출 → 키가 노출되어 탈락
  2. 상시 서버 운영 → 비용 발생
  3. 하루 1번 GitHub Actions에서 생성해 JSON으로 커밋
- **결정:** 3번. 생성은 GitHub Actions가 하고, 앱(GitHub Pages)은 정적 JSON만 읽는다.
- **이유:** OpenAI 호출이 하루 1번이라 비용이 거의 없고, 키는 GitHub Secrets 밖으로 나가지 않으며, Pages와 Actions 모두 무료다.
- **대가:** 실시간 개인화는 불가능하다. 이후 D-10에서 맞춤 설명 기능만 Worker로 예외를 둔다.

## D-02. 알림은 best-effort 수준으로 제한

- **상황:** 매일 정해진 시각에 알림을 보내려면 Web Push 서버가 필요하다.
- **결정:** 서버 없이 가능한 범위로 제한한다.
  - 앱을 열 때 NEW 배지로 알린다.
  - Android Chrome 설치형 PWA에서만 주기적 백그라운드 동기화를 시도한다.
- **이유:** D-01의 서버 없음 원칙을 지키기 위해서. iOS에서 불가능하다는 점은 사용자가 사전에 동의했다.
- **대가:** 알림 시각을 보장하지 않는다.
- **이후 수정:** 처음 구현은 권한만 요청하고 실제로 알림을 보내지 않았다. 이후 커스텀 서비스워커로 바꿔 `periodicsync` 이벤트를 처리하게 고쳤다 (커밋 `b3d1ac6`).

## D-03. 라우터 없이 상태 전환으로 탭 구현

- **결정:** 라우팅 라이브러리 없이 탭을 상태 값으로 전환한다.
- **이유:** 화면이 2~3개라 URL 라우팅이 필요 없다 (YAGNI).

## D-04. 난이도 상향

- **상황:** 처음 설계는 초중급 일상 회화체였다.
- **결정:** 중급~중고급 일상 회화체로 올린다. 관용표현, 구동사, 연어 위주.
- **이유:** 상향 이유는 기록에 남아 있지 않다. 설계 문서에는 "원어민이 실제로 자주 쓰는 톤"이라는 방향만 적혀 있다 (`2026-07-23` spec §2.1, 커밋 `correct pronunciationKo typo and raise word difficulty target`).

## D-05. "퀴즈 없음" 결정을 뒤집고 타이핑 챌린지 추가

- **상황:** 처음에는 하루 1개만 보여주고 퀴즈는 범위 밖(YAGNI)으로 두었다. 그런데 보기만 해서는 표현이 몸에 익지 않았다.
- **결정:** 예문을 정확히 타이핑해야 다른 단어로 넘어가는 흐름을 추가한다.
- **세부 판단**
  - **정답 기준:** 공백과 대소문자는 무시하고 문장부호는 정확히 맞춰야 한다. 너무 엄격하면 짜증나고, 너무 느슨하면 연습 효과가 떨어진다.
  - **오답 처리:** 막지 않고 비교만 보여준다. 학습 흐름이 끊기면 앱을 닫게 된다.
  - **NEW 배지:** 연습으로 다른 단어를 볼 때는 바뀌지 않게 했다.
  - **예문 표시:** 챌린지 중에는 예문을 숨기고 한국어 번역은 힌트로 남긴다 (이후 수정).
- **대가:** 처음 설계 원칙("단순 열람")을 일부 포기했다. 대신 통계와 기록 저장은 계속 범위 밖으로 두었다.

## D-06. 일본어 챌린지는 타이핑 대신 음성인식

- **상황:** 영어와 같은 흐름(오늘의 단어 → 챌린지 → 다음 단어)을 일본어에도 적용하되, 입력 방식만 바꾸기로 했다. 음성인식을 고른 이유는 설계 문서에 따로 적혀 있지 않다.
- **결정:** 브라우저 내장 음성인식(Web Speech API)을 사용한다. 정답은 한자 표기와 히라가나 읽기 둘 다 인정한다.
- **이유 (구현 방식):** 새 의존성이 없다. 인식 결과가 한자로 나올 수도 가나로 나올 수도 있어서 두 형태를 모두 정답으로 인정했다.
- **대가**
  - Firefox 등 미지원 브라우저에서는 통과할 수 없다. 대체 입력은 범위 밖으로 두었다.
  - 오쿠리가나나 다른 한자 표기는 잡지 못한다. 코드에 `ponytail:` 주석으로 한계를 남겼고, 필요해지면 형태소 분석기(kuromoji)를 도입한다.

## D-07. 공통 로직은 훅·팩토리로, 단순 화면은 복제

- **상황:** 영어와 일본어가 같은 흐름(오늘의 단어 → 챌린지 → 다음 단어)을 공유한다.
- **결정**
  - **데이터 로딩:** `createWordApi(basePath)` 팩토리로 일반화했다.
  - **화면 상태:** `useWordOfDayState` 제네릭 훅으로 추출했다.
  - **아카이브 화면:** 로직이 단순해서 추상화하지 않고 복제했다.
  - **localStorage:** 키에 언어 이름을 붙여 영어와 일본어 상태가 섞이지 않게 했다.
- **이유:** 복잡한 상태 로직만 공유하고, 단순한 화면에는 불필요한 추상화를 만들지 않는다.
- **대가:** 3번째 언어를 위한 범용 플러그인 구조는 만들지 않았다.

## D-08. 한글 발음 표기를 LLM에서 규칙 기반 변환으로 교체

- **상황**
  - 처음에는 LLM이 한글 발음(`readingKo`)도 생성했다.
  - 그런데 2026-08-06 단어에서 발음 대신 **번역**을 생성하는 일이 있었다.
  - 결과에 가나가 남거나, 장음 표기가 들쭉날쭉한 문제도 있었다.
- **1차 대응:** "번역이 아니라 발음"이라고 프롬프트를 보강하고 방어 검사를 추가했다 (커밋 `ff3b5ad`).
- **최종 결정:** LLM에 맡기지 않고 히라가나를 규칙으로 한글 변환한다 (`kanaToHangul.mjs`).
- **이유:** 가나→한글은 정해진 대응표로 처리할 수 있는 문제라, 결과가 매번 달라지는 LLM보다 규칙이 정확하고 일관된다.
- **교훈:** 결정적으로 풀리는 문제는 LLM에 맡기지 않는다.

## D-09. 영어 챌린지를 3종 무작위로 확장

- **상황:** 타이핑 한 종류만 반복하니 지루했다.
- **결정:** OX 퀴즈와 단어 순서배치를 추가하고, 챌린지를 열 때마다 셋 중 하나를 무작위로 고른다.
- **이유:** 세 컴포넌트가 모두 `onSuccess`만 호출하게 맞춰서, 기존 훅을 고치지 않고 재사용할 수 있었다.
- **대가:** 일본어 트랙과 드래그 조작은 범위 밖. 문장부호는 별도 조각으로 나누지 않는다.

## D-10. 맞춤 설명은 Cloudflare Worker로 실시간 호출

- **상황:** 사람마다 아는 정도가 달라 같은 설명이 맞지 않는다. 예: 히라가나만 아는 사람에게 한자 단어를 보여주는 경우. 수준별 설명과 후속 질문이 필요해졌다.
- **선택지**
  1. 수준별 설명을 미리 생성 → 질문의 자유도가 없다
  2. 실시간 LLM 호출 + 중간 서버
- **결정:** 2번. 정적 앱(D-01)은 그대로 두고, LLM 호출만 Cloudflare Worker가 담당한다.
- **이유:** Worker는 파일 하나짜리 함수로 충분하고 무료 플랜 범위다. 키는 Worker secret에만 둔다.
- **세부 판단**

| 항목 | 결정 | 이유 |
|---|---|---|
| 로그인 | 없음 | 불특정 다수가 쓰는 개인 프로젝트 |
| 비용 보호 | 출처 검사 + IP당 하루 30회 + 요청 크기 제한 + OpenAI 월 한도(권장 $5, 설정 여부 미확인) | 로그인 없이 쓸 수 있는 수단 |
| 대화 저장 | 안 함. 매 요청에 클라이언트가 대화 전체를 보냄 | Worker에 상태와 DB가 필요 없음 |
| 프로필 저장 | 기기 `localStorage` | 로그인 없음 |
| 대화 한도 | 첫 설명 + 후속 질문 5회 | 비용 상한 |
| 응답 렌더링 | 일반 텍스트만 | XSS 여지 차단 |
| SDK | 쓰지 않고 `fetch`로 직접 호출 | Worker 번들에 의존성 0 |
| 배포 | 수동 `wrangler deploy` | 자주 바뀌지 않음 |

- **대가**
  - 클라이언트가 대화를 새로 시작하면 턴 제한을 우회할 수 있다. 실제 비용 상한은 IP 제한과 OpenAI 월 한도가 맡는다.
  - KV는 읽고 쓰는 사이에 원자성이 없어 동시 요청이 한도를 약간 넘을 수 있다. 정확한 제한이 필요해지면 Durable Objects로 옮긴다.

## D-11. 관련 단어는 벡터 DB 없이 문자 매칭

- **상황:** 설명에 "전에 배운 단어"를 연결하려면 검색 단계(RAG)가 필요하다.
- **결정**
  - **일본어:** 같은 한자를 공유하는 과거 단어를 문자 매칭으로 찾는다. 예: 経験 → 試験
  - **영어:** 공유할 글자 단위가 없어 최근 단어 5개를 넘긴다.
- **이유**
  - 찾으려는 조건이 "같은 한자 공유"라는 글자 단위 조건이라 문자 비교가 가장 정확하다.
  - 아카이브가 수백 개 규모라 벡터 DB가 필요 없다.
- **대가:** 영어 관련 단어가 의미와 상관없이 정해진다. 이 한계는 D-13에서 해결한다.

## D-12. 주간 트렌드 메일을 같은 repo의 GitHub Actions로

- **상황:** Claude Cowork·Code 업데이트가 잦아 매주 정리본을 메일로 받고 싶었다.
- **선택지**
  1. GitHub Actions cron + Node 스크립트
  2. Cloudflare Worker cron
  3. Claude Code 예약 루틴
- **결정:** 1번. 같은 repo에 둔다.

| 항목 | 결정 | 이유 |
|---|---|---|
| 소스 | 공식 블로그 + Claude Code CHANGELOG | 블로그만 보면 작은 기능 업데이트를 놓침. 커뮤니티 소스는 노이즈가 큼 |
| 주기 | 주 1회, 새 소식 없으면 발송 안 함 | 개별 뉴스가 아니라 흐름을 보려는 목적 |
| 발송 | Resend API (`fetch`) | 의존성 0, 무료 |
| 중복 방지 | 날짜 비교 대신 "이미 본 항목" state 파일 | 블로그 목록에 연도가 없고 CHANGELOG에는 날짜가 없음 |
| 링크 | LLM 출력이 아니라 수집 데이터로 조립 | URL 환각 방지 |
| 발송 순서 | 발송 성공 후에만 state 갱신 | 메일 유실 방지 |
| 구조 변경 감지 | 블로그 목록에서 글을 0개 찾으면 job 실패 | 메일이 조용히 끊기는 것을 방지 |

- **구현 중 수정 3건**
  - 첫 드라이런에서 LLM이 블로그 내용을 CHANGELOG 항목에 섞었다. "CHANGELOG 요약은 해당 버전 본문만 근거로" 규칙을 추가했다.
  - 리뷰에서 발견: 메일 발송 후 push가 실패하면 다음 주에 같은 메일이 다시 간다. push 전에 `pull --rebase`하고, 같은 워크플로가 동시에 돌지 않게 했다.
  - 제목의 `&#8217;` 같은 숫자 엔티티가 그대로 보이는 문제를 고쳤다.
- **대가:** 학습 앱과 성격이 다른 기능이 같은 repo에 섞였다. 대신 워크플로와 secret을 재사용할 수 있었다.

## D-13. 영어 관련 단어에 벡터 DB 도입 (의도적 오버스펙)

- **상황**
  - D-11의 영어 "최근 5개"는 오늘 단어와 관련이 없다.
  - 실제로 `get in touch` 설명에 `break the norm`이 들어가자, 모델이 "관련이 없지만"이라고 답했다.
  - 동시에 벡터 DB를 직접 운영해 보는 경험도 목표였다.
- **판단:** 단어 73개 규모에 벡터 DB는 **오버스펙**이다. JSON 파일에 임베딩을 저장하고 직접 유사도를 계산해도 충분하다. 학습 목적이 있어서 이를 알고도 선택했다.
- **적용 범위:** 영어만. 일본어는 D-11의 한자 매칭이 더 정확해서 그대로 둔다.
- **선택지**
  1. 단어 생성 시점에 색인 + Worker가 저장된 벡터로 검색
  2. 요청마다 임베딩 생성 → 지연과 비용이 늘고, 색인용 관리자 endpoint가 필요
  3. 1번과 같되 임베딩을 Cloudflare Workers AI로 → 공급자가 둘로 나뉨
- **결정:** 1번.

| 항목 | 결정 | 이유 |
|---|---|---|
| 벡터 DB | Cloudflare Vectorize | Worker가 이미 Cloudflare, 바인딩으로 바로 사용 |
| 임베딩 | OpenAI `text-embedding-3-small` | 기존 키 재사용, 비용 사실상 0 |
| 벡터 id | 단어 날짜 | 클라이언트·요청 계약을 바꾸지 않아도 됨 |
| 색인 범위 | 매일 아카이브 전체 upsert | 멱등. 하루 실패해도 다음 날 자동 복구, state 불필요 |
| 임베딩 텍스트 | `단어 (품사): 뜻. 예문` | 표기가 아니라 의미가 비슷한 단어가 가깝게 놓이도록 |
| 실패 처리 | 클라이언트가 보낸 최근 5개로 대체 | 검색 실패가 설명 기능을 막지 않음 |
| 유사도 하한 | 두지 않음 | 연결할지는 프롬프트 규칙에 따라 LLM이 판단 |
| 타입 | `@cloudflare/workers-types` 대신 최소 인터페이스 | 기존 `KvStore`와 같은 방식, 의존성 0 |

- **리뷰 반영:** Vectorize가 응답하지 않으면 설명이 무한 대기하는 문제가 있었다. 1.5초 제한을 두고 넘으면 대체 목록을 쓴다.
- **배포하며 확인한 것**
  - REST upsert 본문 형식(raw NDJSON)은 문서가 모호했다. 첫 실제 실행에서 정상 동작을 확인했다.
  - 인덱스를 먼저 만들지 않으면 Worker 배포가 실패한다. 배포 순서를 문서화했다.
- **결과:** `call it a night` → `call it a day`(0.83), `wrap up`, `throw in the towel`, `call off`
- **대가와 전환 조건**
  - 매일 전체를 재색인하는 방식은 단어가 수천 개가 되면 낭비다. 그때 새 단어만 색인하도록 바꾼다 (`ponytail:` 주석).
  - 색인 step이 실패해도 워크플로는 초록불로 끝난다. 실패를 알아채려면 로그를 확인해야 한다.

## D-14. 거절 규칙을 "답할 범위 명시"로 변경

- **상황:** "전에 배운 단어 중에 비슷한 표현 있어?"라는 정상적인 학습 질문을 모델이 거절했다.
- **원인**
  - 규칙이 "관련 학습과 무관한 요청은 거절"이라 범위가 모호했다.
  - `<관련 단어>`가 학습자가 전에 배운 단어라는 설명이 프롬프트에 없었다.
- **결정**
  - `<관련 단어>`가 무엇인지 프롬프트에 명시한다.
  - 답해야 할 범위를 나열한다: 뜻, 발음, 용법, 문법, 예문, 비슷하거나 반대인 표현, 전에 배운 단어와의 비교.
  - 거절 대상은 학습과 전혀 상관없는 요청(코딩, 잡담, 작업 대행)으로 좁힌다.
- **검증**
  - 같은 질문 → `call it a day`를 소개함 (벡터 검색 결과 활용)
  - "파이썬 크롤러 짜줘" → 여전히 거절함
- **교훈:** 거절 규칙은 "무엇을 거절할지"보다 "무엇에 답할지"를 명시해야 과잉 거절이 줄어든다.
